# Local Nightly update testing

Build on the platform being tested (Node 22+ and pnpm 10):

```sh
pnpm update:test:build
```

This builds `3.0.0-nightly.1` and `3.0.0-nightly.2` from the current source. To
choose versions, pass them as arguments, e.g. `pnpm update:test:build
3.0.0-nightly.10 3.0.0-nightly.11`. `package.json` is not temporarily modified.
The updater still uses electron-builder metadata, checksums, ZIP/blockmaps on
macOS and the NSIS installer on Windows. Nothing is published.

## macOS: real automatic installation and relaunch

```sh
pnpm update:test:mac
# Or: pnpm update:test:mac 3.0.0-nightly.10 3.0.0-nightly.11
```

The runner verifies both bundles, copies the older app to a fresh directory
under `tests/Release/apps`, serves the newer artifact on `127.0.0.1:18080`, and
launches the older executable with automatic updates enabled. Success requires
the old app to complete initialization and a **different live PID** to complete
initialization at the installed path with the newer version. Merely reaching
download 100%, changing the bundle version, or exiting does not count as success.
The runner stops only its own test app and local server afterward. It keeps
packages, isolated logs, and a `result.json` under the run directory for diagnosis.
Close an existing test app before repeating the test.

To exercise the manual Download/Restart buttons, run
`pnpm update:test:mac --manual`. The runner keeps the local feed alive while you
use the panel, then verifies the actual relaunch. To intentionally reject an
incompatible macOS signature and inspect whether the error panel remains usable:

```sh
pnpm update:test:mac --expect-signature-failure --hold
```

This re-signs only the disposable installed copy with a per-build ad-hoc
requirement; it does not change either artifact. The runner requires a native
installation-stage signature rejection and the old process to remain alive.
Afterward, close the error panel and test menus/input; press Enter in the runner
terminal to stop the test app and feed.

## Windows: NSIS test and manual panel

1. Run `pnpm update:test:build` on Windows.
2. Run the `.1` NSIS installer in `tests/Release/builds/3.0.0-nightly.1/win`.
3. Serve `.2` in a second terminal:

   ```sh
   pnpm update:test:server --root tests/Release/builds/3.0.0-nightly.2/win --port 18080
   ```

4. Launch **Kawaikara Nightly Update Test**. With automatic updates disabled,
   choose Download and then Restart in the update panel. Verify replacement,
   relaunch, and the runtime version in
   `tests/Release/state/nightly/KawaiData/update-test-runtime.json`.
5. For unattended installation, enable Automatic updates, exit, and repeat
   from the older test installer. Automatic NSIS installation is silent and
   explicitly requests relaunch; manual installation uses installer UI.

For a different port, set `KAWAIKARA_UPDATE_TEST_PORT` to the same value **when
building and running**. The feed and data root are embedded in test builds so
ShipIt/NSIS relaunch does not depend on inherited shell environment variables.

## Isolation and signing boundaries

- Test bundle ID: `day.faby.kawaikara.nightly.update-test`.
- Product: `Kawaikara Nightly Update Test`; updater cache name is also distinct.
- Application/Chromium data: `tests/Release/state/nightly`, never the real
  Nightly profile. The smoke runner never replaces `/Applications` apps.
- No `kawaikara://` registration or Widevine initialization in test builds.
  These tests do **not** validate DRM, Gatekeeper first-launch acceptance,
  production certificate trust, or Authenticode publisher identity.
- As in BDIH Launcher's local tests, macOS uses an ad-hoc signature with a
  stable identifier-only designated requirement. Windows test installers are
  unsigned and disable publisher verification **only in the test config**.
  These are deliberately weaker test settings, not release fixes.
- Release packaging forces the test flag off. The release configuration does
  not import the test config: production signature verification stays enabled,
  and macOS retains certificate-bound requirements. Keep the same signing
  certificate across Nightly builds; notarization is a separate concern.

Squirrel's [signature-validation implementation](https://github.com/Squirrel/Squirrel.Mac/blob/main/Squirrel/SQRLCodeSignature.m)
checks the target against the current application's designated requirement.
The Kawaikara implementation also follows the pinned `electron-updater` 6.8.9
`MacUpdater`/`BaseUpdater` behavior installed in this workspace rather than
assuming the JavaScript download event means native installation is ready.

## Failure behavior and automated checks

The app distinguishes downloading, preparing installation, and installer
handoff. On macOS, Squirrel staging/signature validation happens **before**
window/MPV cleanup, without registering a deferred quit listener. Preparation
then exits PiP, flushes Chromium and preference writes, detaches MPV, and releases
global shortcuts. IPC and site managers remain intact until installer handoff.
Startup failures restore shortcuts/video resources and show a dismissible error
panel. Recoverable installer failures can retry the cached download; invalid
signatures must not be worked around by repeatedly downloading or weakening
release verification. Video playback may need to be resumed after recovery.

```sh
pnpm update:test:unit
pnpm typecheck
```

Tests cover native error/timeout listener cleanup, late readiness, duplicate
restart requests, preparation failure, Windows silent/relaunch arguments,
emitted/thrown installer errors, and cached installation retry.
