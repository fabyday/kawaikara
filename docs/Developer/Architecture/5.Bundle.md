# Bundle, Provider, and Plugin

Kawaikara has one installable extension unit: the **Bundle**. A Bundle contains
one or more **Providers** and may also contain **Plugins**. Bundle kinds are not
split by contribution type.

```text
Bundle (manifest.json)
├── Providers/                       # one or more
│   └── Example/
│       ├── manifest.json
│       ├── Provider.js               # compiled from Provider.ts
│       └── Plugins/                 # zero or more, Provider-scoped
│           └── Helper/
│               ├── manifest.json
│               └── Plugin.js         # compiled from Plugin.ts
└── Plugins/                         # zero or more, Bundle-level
    └── GlobalHelper/
        ├── manifest.json
        └── Plugin.js                 # compiled from Plugin.ts
```

## Ownership

- A Bundle owns distribution metadata, locale support, and shared browser
  profiles.
- Every Provider owns a directory and `manifest.json`. It loads one remote
  service or one app-owned view and becomes a Menu destination.
- A Plugin inside a Provider directory is always scoped to that Provider.
- A Plugin under the Bundle root is global when `providerIds` is omitted. It can
  target specific Providers by declaring `providerIds` in its manifest.
- A Bundle with zero Providers is invalid, even if it contains Plugins.

This physical ownership is also the runtime ownership model. Plugins activate
before their matching Provider loads and deactivate in reverse order before the
Provider is unloaded.

## Runtime definitions

The TypeScript API mirrors the directory model:

```ts
import {
  defineBundle,
  definePlugin,
  defineProvider,
} from '@kawaikara/site-api';

const helper = definePlugin({
  manifest: helperManifest,
  plugin: ExampleHelperPlugin,
});

const example = defineProvider({
  manifest: providerManifest,
  provider: ExampleProvider,
  plugins: [helper],
});

export const bundle = defineBundle({
  id: 'example.streaming',
  name: 'Example Streaming',
  version: '1.0.0',
  apiVersion: 1,
  providers: [example],
  plugins: [],
});
```

Decorators mark runtime constructors; they do not register classes globally.
Static Provider metadata comes from that Provider's manifest. `PluginHost`
receives one explicit `BundleDefinition`, and `SiteManager` stages and validates
all contributions before committing them.

## Provider

```ts
import { AbstractProvider, provider } from '@kawaikara/site-api';

@provider()
export default class ExampleProvider extends AbstractProvider {
  async load(): Promise<void> {
    await this.context.viewer.loadURL('https://example.com/');
  }

  allowPictureInPicture(url: string): boolean {
    return new URL(url).pathname.startsWith('/watch/');
  }
}
```

The Provider manifest owns identity, permissions, and static contributions such
as address hosts, menu placement, shortcuts, locale, profile defaults, and PiP
enablement. The decorator owns settings and site-specific DOM policy in addition
to marking the runtime class. Translated Provider copy lives in a neighboring
`locale.json` source resource.

## Plugin scope

```ts
import { AbstractPlugin, plugin } from '@kawaikara/site-api';

@plugin({ id: 'example.helper' })
export default class ExampleHelperPlugin extends AbstractPlugin {
  activate(): void {
    this.requirePage().register({
      id: 'example-marker',
      source: "document.documentElement.dataset.example = 'true'",
    });
  }
}
```

For a Bundle-level Plugin, `providerIds` in `manifest.json` selects its target
Providers. Omitting it activates one Plugin instance for every Provider. A
Provider-owned Plugin needs no scope declaration because its directory already
defines the owner.

## App / Provider / Plugin contract

Optional features are actual `AbstractPlugin` implementations, registered using
`definePlugin()` in `defineProvider({ plugins })` and the Provider manifest's
`plugins` paths. A Provider-local boolean named `plugins.*` is not a Plugin.
Provider code retains service navigation, authentication, and essential player
policy; independently enabled ad blocking, quality overrides, and short-form
helpers belong to attached Plugins.

App owns one `PluginRuntime` per active Provider. It supplies each Plugin a
separate revocable context, while Provider and Plugins share versioned service
contracts rather than concrete class instances:

| Context API | Responsibility |
| --- | --- |
| `app.logger`, `app.locale` | Plugin-tagged logging and Main-resolved locale |
| `page` | Namespaced injection, document events, execution and input; requires script-injection |
| `network.onBeforeRequest()` | Disposable, synchronous request policies; requires network-interception |
| `actions.register()`, `actions.createUrl()` | Explicit action IDs routed by App; duplicate Plugin owners are rejected |
| `settings.get()`, `settings.onChanged()` | Detached snapshots of this Plugin's declared settings |
| `capabilities.provide()`, `capabilities.get()` | Typed, versioned method contracts within one Provider activation |
| `lifetime.signal`, `lifetime.track()` | Cancellation and idempotent, host-managed resource cleanup |

The old `context.provider` service facade remains for v1 compatibility, but it
is independently revoked and permission-checked too. It is not the Provider
instance. Its `page.dispose()` cannot dispose the Provider's shared pipeline.
`app` is a narrow service facade, not privileged App attachment or Electron access.
These lifecycle fences protect cooperative code; trusted Main-process Bundles
are still not sandboxed against arbitrary direct Node/Electron imports.

### Settings and ON/OFF

Every real Plugin contributes one activation switch to Preferences > Bundles >
its containing Provider. `@plugin({ activation, settings })` may supply localized
copy, a stable activation key, defaults, and additional controls. Without an
activation declaration App uses `plugins.<plugin-id>.enabled`, default ON, with
reload required. Display copy belongs in locale JSON, not Renderer conditions.
`activation` is a boolean setting contribution; `settings` is an array of ordinary
boolean/item-list contributions. Keys must be unique within a Provider.

App persists values under `providerSettings[providerId]`. The same Bundle-global
Plugin therefore has independent desired state and instances for different
Providers. Built-in Plugins retain their previous keys for compatibility.
Execution state (`active`, `disabled`, `failed`, `inactive`) is separately exposed
through the Bundle runtime IPC; an enabled setting does not imply successful
activation. A failed Plugin's controls show its diagnostic when runtime info is loaded.

Use `activation.reloadOnChange: true` for document-world patches. App retires
the old Provider, installs only enabled Plugins, and restores the current HTTP(S)
address. Removing a page registration prevents future injections; it does not
undo JavaScript already executed in the document. Live toggling with
`reloadOnChange: false` is intended for reversible host-side hooks/resources.
The six built-in page enhancements deliberately use reload-on-change.

OFF never calls `activate()`. Disabling or retirement first aborts the Plugin's
signal and revokes its callbacks, actions, network hooks, and capabilities, then
calls `deactivate()`. Cleanup continues if one disposable throws. A Plugin may
use `lifetime.track()` for timers or other resources; releasing a returned handle
manually is safe. `deactivate()` must release resources, not issue new page or
navigation work through the retired context. Already-issued page JavaScript
cannot be forcibly interrupted, but queued injections, subsequent frame
execution, and late API results are cancelled/rejected.

### Interaction and ordering

Use explicit namespaced action IDs for fire-and-forget page/UI commands. App
routes registered Plugin actions first and falls back to the Provider for
unknown IDs. Required return values use a typed capability instead:

```ts
export const playback = defineCapability<{
  next(): Promise<void>;
}>('example.playback', 1);

// Provider or Plugin publishes a service in its activation scope.
context.capabilities.provide(playback, { next: async () => { /* implementation */ } });

// Consumer handles unsupported sites without referencing the producer's class.
await context.capabilities.get(playback)?.next();
```

Only the exact id/version resolves. Services expose methods, not mutable fields.
Duplicate registrations fail. A captured facade or method rejects after either
its producer or consumer retires, even if the same Plugin is enabled again.
Provider services required during Plugin activation should be published in the
Provider constructor or initial `onSettingsChanged()`, before `load()`.
Optional peer contracts must be checked at use time; activation follows Bundle
registration order (Bundle-level Plugins first, then Provider-owned Plugins).
There is no automatic dependency graph or capability-version negotiation.

Network hooks observe the original request. Provider cancellation always wins;
otherwise any Plugin cancellation wins over redirects. Provider redirects have
precedence, then Plugin redirects use descending priority and stable registration
order for ties. Hook/action/settings/activation failures revoke that Plugin and
record a failure without taking down the Provider. Turning it OFF and ON, or
loading the Provider again, retries activation. Shutdown deactivates Plugins in
reverse activation order before Provider unload.

## Validation

The loader validates these rules before registration:

1. Bundle, Provider, and Plugin manifests use schema version 1 and the supported
   Site API version.
2. Bundle IDs, Provider IDs, Plugin IDs, and browser-profile IDs are unique.
3. The Bundle declares at least one Provider directory.
4. Every compiled JavaScript entry stays inside its owner.
5. Manifest identity and static contributions are canonical.
6. Top-level Bundle permissions cover every Provider manifest permission.
7. A Provider default browser profile exists in its Bundle.
8. Provider-owned Plugin scope cannot exclude its owner.

Registration is atomic. A failed Bundle does not leave a partial Provider or
Plugin registration behind.

## Version and permission boundaries

The Bundle version is the release and update version. Provider and Plugin
versions remain in their child manifests for compatibility diagnostics, data
migrations, and support logs, but Kawaikara does not update a child separately
from its Bundle.

The top-level Bundle permission list is the installation consent boundary. Each
Provider manifest declares the smaller capability set used by that Provider,
and it must be a subset of the Bundle list. Runtime contexts are constructed
from the Provider manifest permissions, never from decorator code.

## Code ownership and attachment

Site-specific injection belongs beside its Provider, normally under
`Providers/<name>/Inject/`. Kawaikara core owns only reusable primitives such as
script serialization, lifecycle hooks, safe action URLs, and generic PiP
layout. This keeps remote-DOM hacks updateable with the Bundle that understands
that site.

Provider-owned Plugins attach to exactly that Provider. A Bundle-level Plugin
can attach to several Providers with `providerIds`, or all Providers when the
field is omitted. Version 1 intentionally does not allow third-party Plugins to
attach directly to the App: App attachment would expose a different privileged
context and therefore needs a separate permission model and API version.

`kawaikara.video` is a Provider that selects the app-owned `video-library`
internal panel. The renderer and playback backend remain App code. Other
Providers and Plugins may contribute sandboxed HTML PluginView panels. Their
owner id plus local panel id is canonical; titles are allowed to repeat.

## External installation

Preferences > Bundles accepts `.kawai` archives (ZIP containers) with `manifest.json` at the archive
root or inside one enclosing directory. Kawaikara validates compressed size,
expanded size, entry count, path traversal, symbolic links, every nested
manifest, compiled entry paths, IDs, SemVer, and API versions. A valid Bundle is
moved to `KawaiData/Bundles/<bundle-id>` and becomes active after restart.

An optional top-level `update` declaration enables the Update action for both
built-in and user Bundles. It can contain a credential-free HTTPS archive URL
or a compiled resolver entry that returns one for the current app channel,
platform, and architecture. The downloaded archive is subject to the same
limits and must keep the existing Bundle id. User Bundles can also be removed;
built-in Bundles cannot. Changes to running code take effect after restart.

Before moving the Bundle, Kawaikara shows every requested Provider permission
and requires an explicit `Allow and install` choice. Denying the request cancels
installation and deletes the temporary extracted directory.

The current loader is a trusted-code model. Provider and Plugin TypeScript is
compiled to JavaScript before packaging; those modules execute in Main and can
access Node.js during module initialization. Archive
validation prevents unsafe extraction but is not a sandbox or publisher
signature. Install only Bundles from trusted sources.

See [Packaging](../Plugins/4.Packaging.md) for the complete archive format.

Provider-owned OS file-drop routing, Global/Local scopes, and the planned manual
conflict chooser are described in [Drag and drop](6.DragDrop.md). The current
implementation registers only Video's app-owned local-file playback action.
