# Provider-registered drag and drop

## Status and boundaries

Implemented now: OS **local video files** route through Main's
`DragDropManager`. The built-in Video Provider declares a Global file-drop
contribution. Existing playback, first-supported-file handling, and the drag
overlay are preserved. No new player is created when the Video view is already
active.

The scope matcher understands Global and Local, but Video's Global registration
is the only built-in consumer. The manual conflict chooser, non-video adapters,
URL/text/folder payloads, Plugin registrations, and remembered choices below are
**design contracts, not shipped UI or capabilities**.

## Ownership

| Layer | Responsibility |
| --- | --- |
| Preload `DragDrop` | Capture the OS gesture, prevent browser file navigation, extract paths with `webUtils`; display feedback without changing focus or playback |
| Main `DragDropManager` | Validate payload, match registered owners, scope and file type; serialize drops; never silently choose among overlapping owners |
| `SiteManager` | Register declarations only after successful Bundle validation; unregister on removal/rollback/development reload |
| Provider manifest | Declare supported payload and destination, even while its page is inactive |
| App action adapter | Carry out the selected action with the app-owned services and permissions |

This is not another extension ownership model. A Bundle still owns Providers
and Plugins. `Global` is **drop targeting scope**, not permission for a
Provider-local Plugin to become an App Plugin. Main remains the policy owner;
preload and renderer never decide which Provider to activate.

## Current registration

In `Providers/Video/manifest.json`:

```json
{
  "permissions": ["internal-view", "plugin-view"],
  "contributes": {
    "fileDrop": {
      "scope": "global",
      "extensions": [".mp4", ".mkv", ".webm"],
      "action": "open-local-video"
    },
    "menu": { "category": "Video" }
  }
}
```

The example abbreviates the normal manifest header and supported extension list.
`fileDrop` is manifest-owned, not decorator metadata. Each Provider can declare
one route in this phase. Extensions are unique lowercase dotted suffixes. Main
normalizes incoming suffix case and checks that an absolute path is a real file.
Extensions indicate an eligible handler, **not proof that a file can decode**.
The playback backend performs that validation and reports its own errors.

`open-local-video` is the only implemented action and requires `internal-view`.
It delegates to the existing app-owned Video surface; it is not a general-purpose
`onDrop` callback for external pages. A declaring Provider must load the Video
internal view. Additional actions need their own adapter and permission contract;
do not add a Provider-ID switch inside preload.

Registrations exist while the Bundle is installed/registered, not just while
`Provider.load()` is active. Global discovery must not instantiate every Provider
or run side-effecting `canHandle()` callbacks. The current registry copies
contribution data and revokes it with its owner.

## Global and Local

- **Global**: eligible over any Provider. After the user drops, activate the
  selected owner only when necessary.
- **Local**: eligible only when the drop target's active Provider is its owner.
  It must not navigate to an inactive owner to make itself eligible.
- Menu/preferences layers retain the underlying active Provider as their target.
- Global and Local are eligibility rules, **not priorities**. Neither Local,
  the current Provider, nor the first registered Provider automatically wins.
- Revalidate owner existence and Local scope after asynchronous file checks.
  A removed registration cannot receive a delayed drop.

## Matching and conflicts

One OS gesture is one routing operation. Validate and deduplicate paths, gather
eligible owners, then act:

1. No candidates: show unsupported feedback; keep the current source intact.
2. One candidate: hand off once. Video opens the first supported file, not an
   implicit playlist and not one player per file.
3. Multiple candidates: return `selection-required` with owner IDs and titles;
   **do not navigate, enqueue video playback, or run any handler**.

Today the third result displays explanatory feedback and leaves files unopened.
Until the chooser is implemented, the user can open from their desired Provider
directly. Overlaps are valid registrations, not a Bundle installation error.

### Manual chooser contract — next phase

Present eligible Provider/action labels after drop, with matched file count and
payload summary. The user chooses one explicitly or cancels (Escape/X). Cancel
must preserve source, playback position, and current Provider. Do not auto-pick
based on registration order, active site, scopes, or past use. Remembering a choice
would require a separate explicit user preference and is not enabled by default.

Main should retain a short-lived request token containing the validated files,
source Provider, and candidates. The renderer sends only token + selected owner;
it cannot manufacture file paths or candidates. Consume the token at most once.
Expire on cancellation, replacement, Bundle removal, or timeout. Revalidate file
availability and owner/scope on selection. If the target changes while a Local
choice is pending, cancel or recompute rather than using stale authority.

For mixed multi-file drops, show which files each candidate accepts. Never split
one gesture between several Providers without a separate explicit user choice.

## Future payloads — not implemented

### Provider execution contract

When additional Provider behaviors are implemented, replace the single-route
declaration with stable, owner-namespaced handler IDs. A manifest declares each
handler's payload filters and scope; the selected Provider receives the validated
payload through a narrow lifecycle method such as `onDrop(handlerId, request)`.
This method is a proposed API, not currently exported. Do not grow a core
`switch (providerId)` or require every remote Provider to use the Video adapter.

Only the selected handler may execute. Main activates the owner when needed,
then invokes it with an abortable request; scope loss, removal and superseding
requests revoke further operations. A handler returns handled/rejected/failure
explicitly. Rejection must not automatically try another Provider, which would
bypass the user's choice. App-owned media/file access still goes through narrow
context capabilities; never pass a BrowserWindow, ipcMain or the entire app to
a Provider. The current Video adapter's queue-before-activation behavior must
remain available so generalization does not reintroduce player reloads or a
folder-view flash.

### Payload registration

Use a discriminated payload (`files`, `directories`, `url`, `text`), with bounded
data and explicit per-type declarations. MIME can be a hint, not sole validation;
URL schemes need an allowlist. Directory recursion, URL fetching, downloads, and
file content reads must not occur during `dragenter`/`dragover` or candidate probing.
Each new adapter must specify batch semantics and a narrow permission boundary.
Plugin routes, if added, inherit their Bundle/Provider ownership and ON/OFF
lifetime; they must use the same resolver and conflict chooser.

## Performance and safety

- Hover feedback is local DOM state; no per-frame IPC, file reads, player changes,
  native overlay-window creation, or Provider reloads.
- Only preload obtains real OS file paths. Main bounds one request to 256 paths,
  rejects relative/NUL paths, skips inaccessible files and directories, and never
  evaluates dropped text as JavaScript or HTML.
- There is one in-flight handoff. Overlapping requests return `busy`; failures
  release the gate. This is not a queue of repeated player initializations.
- Existing Video playback is reused. Cross-Provider drops use the existing
  transition path only after a unique route is resolved.
- The drag overlay currently uses the Video messages supplied by Main from root
  `locales/`. General payload-specific overlay copy belongs to the future UI phase.
- Trusted Main-process Bundles are not a sandbox. Drop validation is not a grant
  of arbitrary filesystem or network access to web pages.
